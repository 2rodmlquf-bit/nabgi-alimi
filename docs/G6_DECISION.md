# G-6 결정 정리: Supabase 도입의 시점과 데이터 범위

Phase 10을 시작하기 전에 **사용자가 정할 것**을 정리한 문서다. 아직 아무것도 정해지지 않았고, 정해지면 `docs/DECISIONS.md`의 G-6에 옮겨 적는다. (Supabase의 기능·제한·가격은 착수할 때 공식 문서로 다시 확인한다. 이 문서는 그것을 확인하지 않았다.)

## 1. 지금 상태 (사실)

- 앱은 v0.5.0까지 **로컬 전용**이다. 저장은 `%APPDATA%\delivery-watch\state.json` 한 파일이고, 화면은 저장 방식을 모른다 (`src/store`의 `load/save/clear/info` 인터페이스).
- 준비된 것: 기록마다 UUID `id`와 `createdAt`, 삭제 표시 `deletedAt`, `schemaVersion`과 이전 규칙, 두 저장소(파일·메모리)가 같은 **계약 시험**을 통과한다. `SupabaseStore`는 이 계약 시험을 그대로 통과해야 한다.
- 외부 통신 코드는 지금 한 곳(Claude API, 사용자가 키를 넣었을 때만)이다. DB를 붙이면 **"모든 데이터는 이 컴퓨터에만 저장한다"는 PRD 비기능 요구가 깨진다**(Supabase 모드일 때). PRD 개정이 필요하고, `test/security.test.js`의 "fetch는 한 곳뿐" 시험도 의도적으로 바꿔야 한다.

## 2. 계획서(`devpian.md` Phase 10)를 읽으며 찾은 문제 3가지

착수 전에 고쳐야 하는 것이다.

1. **스키마 초안이 G-8을 모른다.** 초안은 `inform_logs.status check in ('지연','임박')`인데, 이제 안내 기록의 상태에 **`확인필요`**가 들어간다 (납기를 모르는 주문도 안내 대상). 초안대로 만들면 그 기록은 DB가 거부한다.
2. **"최소 데이터"도 민감하다.** 올리기로 한 안내 기록·메모에는 주문번호(`order_no`)와 **자유 입력 글**(안내 메모, 전화 소식)이 들어간다. 그 글에 사람 이름·공급사 이름·일정이 적힐 수 있다. 주문 원본(품목, 연구원 이름 열)을 안 올려도 회사 데이터를 올리는 것이다.
3. **`legacy` 영역이 비어 있다.** 공급사 연락 기록(`contactLog`), 대체품, 분납 일정은 "S1 범위 밖"이라 DB로 옮기지 않기로 했다. 그러면 `SupabaseStore`는 이 값을 **로컬에 따로 남기는 혼합 저장소**가 되어야 한다. 안 그러면 DB 모드에서 이 기록이 사라진다. 두 번째 기기에서는 이 기록이 보이지 않는다.

그 밖에 새로 생기는 것: 로그인 화면과 동기화 상태 표시(IA에 새 화면), 오프라인 대기열·충돌 규칙(안내·메모는 충돌이 거의 없고 설정·주문 메타는 최신 쓰기가 이김), 사용자 간 격리를 지키는 RLS 시험, `service_role` 키를 앱에 넣지 않는 규칙.

## 3. 정해야 할 것 5가지

### ① 왜 DB가 필요한가 (이게 범위를 정한다)
| 선택 | 의미 |
|---|---|
| **A. 학습·포트폴리오 (추천)** | 수업·포트폴리오에서 "로컬 저장소를 DB로 교체해도 화면이 안 바뀐다"를 보이는 것이 목적. 가상 데이터, 본인 계정 하나 |
| B. 여러 기기에서 쓰기 | 집·회사 PC 동기화. 오프라인 대기열이 필수가 되어 범위가 커진다 |
| C. 백업 | 파일 내보내기로도 되는 일이라 DB의 이유로는 약하다 |
| D. 여러 담당자 공유 | 사용자 간 공유·권한이 필요. 지금 설계(본인 행만 접근)로는 안 된다. 별도 PRD |

### ② 어떤 데이터로 쓰나
| 선택 | 의미 |
|---|---|
| **가상 데이터만 (추천)** | 개인 Supabase 프로젝트에 샘플 데이터로만. 보안 문제 없음 |
| 회사 업무 데이터 | **보안 게이트 통과 전에는 하지 않는다.** 회사 정보보안 승인이 필요할 가능성이 높고, 승인이 없으면 로컬 전용을 유지한다. 입사 후에 다시 결정 |

### ③ 무엇을 올리나
| 선택 | 의미 |
|---|---|
| **안내 기록·메모·설정·주문 메타(사유·원인 지정·납기 변경) (추천)** | 계획서의 최소 데이터 원칙. 주문 원본은 매번 엑셀로 불러오므로 올리지 않는다 |
| 위 + 공급사 연락 기록 등 `legacy` | 범위가 늘고 테이블이 3~4개 더 생긴다 |
| 전부 (주문 원본 포함) | 하지 않는다. 데이터가 커지고 위험도 커진다 |

### ④ 시점
| 선택 | 의미 |
|---|---|
| **지금 Phase 10을 시작 (가상 데이터 전제)** | 수업 진도에 맞춘다. 먼저 별도 PRD(범위·로그인·동기화)를 짧게 쓰고 시작하는 것을 권한다 |
| 깨끗한 환경 설치 시험(M-10)을 먼저 | v0.5.0의 조건부 go 조건을 닫고 시작. 이 PC에서 못 한 것이라 새 PC·샌드박스가 필요 |
| 보류 | 입사 후 실제 요구를 알고 나서 |

### ⑤ 지켜야 할 원칙 (이견이 없으면 그대로 확정)
- 저장 방식은 `storageMode`(`local` 기본, `supabase`)로 고르고 **로컬이 항상 폴백**이다. 기본값은 계속 로컬.
- 접속은 메인 프로세스에서만 하고, 앱에는 공개(anon) 키만 넣는다. **`service_role` 키는 앱에 넣지 않는다.**
- 로컬 → DB 이전은 한 번, 사용자가 확인한 뒤, id 기준 멱등으로, 이전 전에 백업한다.
- 종료 조건: 계약 시험이 두 저장소에서 통과, RLS 시험(남의 행 접근 불가), 두 모드에서 E2E 여정 동일.

## 4. 추천 조합

**① A (학습·포트폴리오) + ② 가상 데이터만 + ③ 안내 기록·메모·설정·주문 메타 + ④ 별도 PRD를 먼저 쓰고 시작 + ⑤ 그대로.**
이유: 지금 목적이 포트폴리오·수업이고, 회사 데이터를 쓸 수 없는 상태이며, 로컬 전용 v0.5.0이 이미 완성되어 있어 DB가 실패해도 잃는 것이 없다. `legacy`는 로컬에 남기는 혼합 방식으로 두고(③의 세 번째 문제), 다기기 동기화(B)는 첫 버전에서 뺀다.

## 5. 정해지면 할 일 (Phase 10 첫 작업)

1. 이 문서의 결정을 `DECISIONS.md` G-6에 확정으로 기록하고 PRD 비기능(데이터 위치, 외부 통신)을 개정한다.
2. 스키마 초안에 `확인필요`를 넣고 `legacy` 처리 방식을 정한다.
3. 별도 PRD(`prd_supabase.md`)에 범위·로그인 화면·동기화 규칙·종료 조건을 쓴다.
4. 그 다음에야 개인 Supabase 프로젝트를 만든다 (계정 가입과 키 발급은 **사용자가 직접** 한다).
