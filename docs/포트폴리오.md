# 납기 알리미 — 포트폴리오 정리

> **[직접 채워 주세요]** 이름 / 연락처 / 지원 직무 / 이 프로젝트에서 내가 한 일 (아래 "내 역할" 참고)
> 이 문서는 면접·포트폴리오 설명용 초안입니다(v0.5.0 기준으로 갱신). 확인한 것과 확인하지 못한 것을 구분해서 적었습니다. **"업무 시간을 얼마 줄였다" 같은 효과 수치는 여전히 넣지 않았습니다.** 실제 업무에서 측정한 적이 없기 때문입니다. 대신 **개발하면서 잰 숫자**(화면 스크롤 양, 처리 시간, 테스트 개수)만 근거와 함께 적었습니다.

## 1. 한 줄 소개

공급사 납기 회신이 이메일·엑셀·사내 프로그램에 흩어져 **지연 조짐을 늦게 알아채는 문제**를, 납기 임박·지연 주문을 골라 보여 주고 이메일·엑셀의 납기를 읽어 확인 후 반영하는 데스크톱 앱으로 풀어 본 프로젝트.

## 2. 문제 → 접근 → 결과 → 한계

## 3. 내 역할 (직접 다듬어 주세요)

AI(Claude)와 함께 만든 프로젝트입니다. 면접에서는 **누가 무엇을 결정했는지**를 분명히 말하는 게 좋습니다. 아래는 이 프로젝트에서 실제로 있었던 일을 기준으로 한 초안입니다.

- **내가 한 일(결정)**: 풀 문제를 정의하고, 인터뷰 질문에 답하며 요구사항을 정했다(사용자 범위, API 키 없이도 동작, 빈칸은 "미회신"으로 모아 재문의, 달라진 것만 표로 보고 일괄 반영, 말투·호칭·서명, 원인 분류 방향). 막연한 부분은 "이 질문엔 답하기 어렵다", "단계가 너무 복잡하다", "해결을 도와주는 느낌이 부족하다"처럼 피드백해서 방향을 바꿨다.
- **개발 단계에서 내가 내린 결정**: 확인 필요 주문을 표 맨 아래에 보이고 안내 기록도 가능하게 할지(G-8, A안), 각 단계를 시작하라는 승인, 이 PC의 기존 설치본을 지키려고 **설치 시험을 건너뛰기로 한 것**, Supabase는 학습·포트폴리오 목적·가상 데이터·안내 기록/메모/주문 메타/설정만·다기기 제외로 한 것(G-6).
- **AI가 한 일**: 코드 작성, 테스트 작성, 실제 앱 실행 확인, 측정, 문서 초안.
- **내가 확인한 일 [직접 확인해서 채우세요]**: 앱을 직접 실행해 샘플로 눌러 보기, 불편한 점 피드백 등.

## 4. 2분 데모 순서 (v0.5.0: 안내 추적 중심)

핵심 솔루션(S1)을 보여 주는 순서입니다. 이메일·공급사 엑셀 쪽은 아래 4-1에 따로 두었습니다.

1. **(15초)** 「샘플 불러오기」. 맨 위 **안내 현황 막대**: "미안내 15" — 지금 연구원에게 알려야 할 건이 몇 건인지가 첫 화면에서 보인다는 것이 핵심.
2. **(45초)** 「안내가 필요한 것만 보기」 → 표에서 연구원 칸을 눌러 한 명의 건만 거르기 → 「이 연구원에게 한 통 안내문」 → **복사**하면 「이 N건 안내함으로 기록」이 강조됨(자동으로 기록하지는 않음) → 누르면 막대 숫자가 바뀜.
3. **(20초)** **다시 안내**: 기준일을 8일 뒤로 바꾸면 "다시 안내"가 되고 **이유**("7일째 새 소식을 알리지 않았어요")가 보인다. 기준 일수는 품목별 임박 기준 패널에서 바꿀 수 있다.
4. **(20초)** **빠른 메모**: 전화로 들은 소식을 글 하나로 남기고 표의 "메모 1"을 확인. 이어서 마우스 없이 표에서 화살표 → Enter → Tab Tab → Enter로 기록하는 것을 보여 준다.
5. **(10초)** 「목록 열기」로 `.xlsx`를 열면 CSV와 같은 결과. 5,000줄이 넘는 파일은 "일부만 읽었다"고 알린다.
6. **(10초)** 마무리: "가상 데이터로만 검증했고, 측정한 숫자는 이렇습니다(스크롤 1,374px → 0, 5,000행 0.43초). 못 한 것은 깨끗한 PC에서의 설치 시험입니다."

## 4-1. 확장 기능 데모 (이메일 추출·공급사 엑셀)

1. **(15초)** 첫 화면에서 "납기 알리미가 무엇인지" 한 문장. 「샘플 불러오기」 → 지연 7·임박 6·확인 필요 2.
2. **(25초)** 표에서 PO-2026-1002를 눌러 상세 → "지연 원인이 비고에서 자동 분류(통관·서류)되고, 틀리면 드롭다운으로 직접 수정". 「안내문 만들기」 → 격식 있는 안내문이 나오고 복사만 하고 **보내지는 않는다**.
3. **(40초)** 「이메일 납기 추출」 → **메일 폴더에서 읽기** → 「샘플 메일 폴더 열기」 → 「지난주 금요일 ~ 오늘 오전」. 4통에서 주문 4건. 포인트: "빠르면 이번 주 중"은 날짜를 **지어내지 않고** 확인 필요, 근거 문장 표시, 더 최근 메일 우선.
4. **(30초)** **공급사 엑셀 읽기** → 샘플 2: 첫 시트가 안내문이어도 표 시트를 찾고, 제목 줄·열 이름이 달라도 머리글을 찾는 것, 빈칸·"확인 후 회신"을 **미회신**으로 모아 재문의 문구가 나오는 것.
5. **(10초)** **오늘 연락할 곳**: 공급사별로 묶여 급한 순서, 「연락함으로 표시」.
6. **(마무리)** "가상 데이터로만 검증했다는 한계"와 "입사 후 하고 싶은 것"을 말한다.

## 4-2. 현업 경험을 설계에 반영한 사례

"공급사가 메일·카톡·문자를 읽고도 답하지 않고, 전화하면 사과만 하고 늦게 보내는" 경험에서 **무응답 대응**을 만들었습니다. 실제로 했던 조치(전화 재촉 → 연구원에게 지연 가능성 사전 안내 → 다른 담당자·상급자 경유 → 대체 공급사·대체품 검토, 반복되면 업체 교체)를 앱의 **단계**로 옮겼습니다. 연락 이력(채널·횟수), 구두로 들은 날짜가 지켜졌는지, 단계별 문구가 들어 있습니다. *(실제 업체 이름은 쓰지 않았습니다. 면접에서도 이름 대신 "반복 무응답 업체"로 말하는 것이 안전합니다.)*

두 번째 사례는 **부분 납품과 말없는 대체품**입니다. 수량이 모자라게 들어온 주문을 입고 완료로 빼지 않고 남은 수량만 지연·임박으로 관리하며, 공급사가 알려 준 분납 일정을 수량별로 기록합니다. 회신의 규격·품명이 주문과 다르거나 "동급·대체" 같은 말이 있으면 대체품 의심으로 표시하고, 항목별 비교와 함께 연구원 승인 요청·공급사 사전 승인 요구·반려 문구를 만들어 줍니다. *(대체 여부 판정은 규칙 기반 가정이며 가상 데이터로만 확인했습니다.)*

## 5. 만들면서 찾아 고친 문제들 (면접에서 말하기 좋은 실제 사례)

"AI가 만든 코드를 어떻게 믿나요?"에 대한 답이 됩니다. **직접 실행해서 확인하다가 찾았고, 테스트로 남겼습니다.**

| 무엇이 문제였나 | 어떻게 찾았나 | 고친 방법 |
|---|---|---|
| 이메일로 납기를 바꾸면 그 주문이 "정상"이 돼 예외 목록에서 **사라져서**, 정작 "납기가 바뀌었다"고 연구원에게 알릴 안내문을 만들 수 없었다 | 안내문 흐름을 실제로 끝까지 눌러 보다가 | 이메일 결과 카드에서 바로 안내문을 만들 수 있게 함 |
| 두 날짜가 있는 이메일에서 출항일과 도착일이 둘 다 "출발"로 분류돼 도착일을 못 고름 | 실제 공급사 이메일이 없어서 흔한 표현을 **정답과 함께 가상으로 19가지 만들어** 규칙을 돌려 보니 9개가 틀림(이후 23가지로 늘림). 틀린 것을 하나씩 따라가다 발견 | 두 날짜 사이의 글자가 양쪽 날짜에 섞이지 않게 라벨 붙이는 방식을 고침 |
| 주문번호가 문장 앞이 아닐 때 날짜 위치 계산이 어긋날 수 있었음 | 위 버그를 따라가며 코드를 읽다가 **잠재 문제로 발견**(재현한 것은 아님) | 위치를 더하는 순서를 바로잡음. 이 항목은 "재현해서 찾은 버그"가 아니라 "코드를 읽다 고친 것"으로 말해야 정직함 |
| 막대 그래프의 길이가 그려지지 않음 | 앱을 띄워 콘솔을 보니 보안 정책(CSP)이 `style` 속성을 막고 있었음 | 스타일을 코드로 지정하도록 바꿈 |
| `1/2인치`가 1월 2일로, `2.5톤`이 2월 5일로 읽힐 위험 | 규칙을 설계하며 반례를 먼저 떠올림 | 납기 관련 말이 가까이 있을 때만 날짜로 보고, 규격 단위가 붙으면 제외 |
| 가상 메일의 보낸 사람 이름이 깨져(`게동펑찡`) 보임 | 앱을 돌려 결과를 출력해 보다가 발견 | 파서가 아니라 제가 만든 샘플의 인코딩 값이 틀린 것이었음. 고치고 테스트로 남김 |
| 공급사 샘플 2 버튼이 샘플 1을 열고 있었음 | 두 번째 파일 결과를 출력해 보니 첫 번째 파일 결과 | 앱 연결부에서 어느 샘플인지 값을 넘기지 않던 것을 고침 |
| 공급사가 보낸 메모에 `=HYPERLINK(...)`가 있으면 CSV를 엑셀로 열 때 수식이 실행될 수 있음 | 내보내기를 설계하며 위협을 먼저 생각 | 글자 칸이 `=+-@`로 시작하면 `'`를 붙이고, 일부러 그런 메모를 넣은 주문으로 확인 |

## 5-2. 개발 단계(Phase 0~9)에서 측정하고 찾아 고친 것

위 5번 표가 기능을 만들 때의 사례라면, 이 표는 **계획 → 구현 → 측정 → 릴리스 검증** 단계에서 나온 사례입니다. 모두 `docs/BACKLOG.md`·`docs/AUDIT.md`에 기록돼 있습니다.

| 무엇이 문제였나 | 어떻게 찾았나 | 고친 방법 |
|---|---|---|
| 빠른 메모를 4건 남겼는데 저장 파일에는 13건이 있었다. **새 기록이 저장할 때마다 복제**되고 앞의 것에는 삭제 표시가 붙었다 | 새 기능의 E2E 시험(저장 파일을 직접 열어 건수 확인)이 실패 | 저장소가 id 없는 새 기록을 내용·시각이 같은 기존 기록과 맞춰 보게 고침. 같은 구조였던 안내 기록도 함께 해결. 단위 시험으로 고정 |
| 주문을 열어도 "안내함으로 기록" 버튼이 화면 밖에 있었다 | "스크롤해야 했던 것 같다"는 느낌이 아니라 **창 크기별로 px을 쟀다**: 1,374px | 영역 순서를 바꿨더니 **33px이 모자랐다.** 좁은 칸에서 채널·메모·버튼이 3줄로 접혀서였다. 버튼을 상태 줄 바로 아래로 올려 0px |
| 좁은 창에서 주문을 누르면 상세로 내려가는데 **고정 머리가 상세 위쪽을 가렸다** | 자동 시험은 통과했지만 **스크린샷을 눈으로 보다가** 발견 | 머리 높이만큼 비우고 스크롤. 시험도 "머리에 가려지지 않음"까지 확인하도록 강화 |
| 표 줄·정렬 머리글·연구원 필터는 마우스로만 눌렸다. 체크박스·검색칸 등 20여 곳에 이름이 없었다 | 접근성 점검 도구로 **개수를 먼저 쟀다**(전체 15줄이 키보드로 못 닿음) | 한 줄만 탭 정지로 두고 화살표로 이동, 모든 요소에 이름. 측정값 0 |
| 앱을 두 개 띄우면 같은 저장 파일을 서로 덮어써 기록이 사라질 수 있었다 | 계획서의 오류 경로 점검에서 "마지막 저장이 이긴다"는 문장을 읽고 위험으로 판단 | 한 개만 뜨게 잠금. 두 번째 실행은 창을 앞으로 가져오고 끝난다 (E2E로 확인) |
| 저장 한도(2MB)에 닿으면 갑자기 저장이 거부됐다 | 규모를 계산해 보니 건당 안내 3건이면 주문 3,860건에서 닿음 | 80%부터 미리 경고. 100%는 거부하되 기존 내용은 그대로 |
| 전체 시험을 돌릴 때만 가끔 실패했다 | 단독 재실행에서는 통과해서 **앱이 아니라 시험의 문제**로 의심, 원인을 하나씩 확인 | 저장 전에 먼저 쓰인 빈 파일을 읽던 경쟁 상태, 창이 가려지면 멈추는 색 전환 애니메이션 → 시험을 고침. 앱 코드는 그대로 |
| **AI가 "태그를 달고 올렸다"고 보고했는데 실제로는 명령이 실패해 아무것도 올라가지 않았다** | 다음 단계를 시작하며 태그 목록과 원격 상태를 확인하다 발견 | 바로 바로잡고 사실대로 알림. 이후에는 단계마다 태그와 푸시를 확인하는 단계를 둠 |
| 계획서의 DB 스키마 초안이 '확인 필요' 안내 기록을 거부하게 되어 있었다 | Supabase 결정 문서를 쓰며 앞서 바꾼 결정(G-8)과 대조 | 초안의 문제 3가지를 `docs/G6_DECISION.md`에 적고 PRD에서 고치기로 함 |

## 6. 예상 질문과 답변 초안

**Q. 앱을 실제로 돌려 보다가 찾은 문제는?**
A. 대체품 확인 기능은 단위 테스트가 모두 통과했는데, 실제 화면에서는 규격만 다른 대체품(6204ZZ → 6204-2RS)이 잡히지 않았습니다. 화면이 규격·수량 열을 비교 함수에 넘기지 않고 있었기 때문입니다. 테스트가 화면 연결까지 보장하지 않는다는 것을 배웠고, 고친 뒤 앱에서 다시 확인했습니다.

**Q. 현업 경험이 앱에 어떻게 들어갔나요?**
A. 가장 힘들었던 사례가 "연락해도 읽고 답이 없는 공급사"였습니다. 그때 실제로 했던 순서(전화 재촉, 연구원에게 미리 알림, 상급자·다른 담당자 경유, 대체 공급사 검토)를 무응답 횟수에 따른 4단계로 만들고, 단계마다 보낼 문구를 만들어 줍니다. 구두로 들은 날짜가 지켜지지 않았는지도 기록합니다. 단계 기준은 제 경험에 기반한 가정이고 실제 업무로 다듬어야 합니다.


**Q. 왜 AI 호출을 선택 사항으로 했나요?**
A. 비용 때문에 키가 없는 상황에서도 핵심이 돼야 했고, 회사 메일을 외부로 보내는 것이 보안 규정에 걸릴 수 있다고 봤습니다. 그래서 규칙 기반 추출을 기본으로 하고, 규칙이 못 읽는 것만 Claude가 도울 수 있게 선택으로 뒀습니다. (단, Claude 호출은 실제로 해 보지 못했고 예시 응답으로만 확인했다고 말씀드립니다.)

**Q. 이메일에서 읽은 납기가 틀리면 어떻게 되나요?**
A. 자동으로 목록을 바꾸지 않습니다. 변경 전후 날짜, 근거 문장, 신뢰도를 보여 주고 사람이 누를 때만 반영합니다. 근거 문장이 이메일 원문에 없으면 반영 버튼을 막고, 애매한 표현은 날짜를 지어내지 않고 "확인 필요"로 남깁니다.

**Q. 가상 데이터로만 검증했다는 게 약점인데요?**
A. 맞습니다. 그래서 실제처럼 지저분한 가상 입력(합친 제목 줄, 열 이름 변경, EUC-KR 메일, 답장 인용, 같은 주문 두 줄 등)을 일부러 만들어 돌렸고, 한계를 문서에 그대로 적었습니다. 입사하면 실제 데이터로 가장 먼저 규칙을 검증하겠습니다.

**Q. 공급사가 엑셀을 마음대로 바꿔 보내면?**
A. 앞쪽 40줄에서 머리글처럼 보이는 줄을 찾고(주문번호·납기 같은 말이 가장 많이 맞는 줄), 시트가 여러 개면 표가 있는 시트를 고릅니다. 그 결과를 확인 화면에 보여 주고 틀리면 사람이 고치게 했습니다. 빈칸은 기존 납기를 지우지 않고 "미회신"으로 모아 재문의 문구를 만듭니다.

**Q. 왜 메일 서버에 직접 연결하지 않았나요?**
A. 회사 IT의 승인과 보안 검토가 필요한 일이라, 승인 없이 지금 할 수 있는 중간 단계로 `.eml` 파일 폴더 읽기를 만들었습니다. 입사 후 규정을 확인한 뒤 읽기 전용으로 연결하는 것이 다음 단계입니다.

**Q. 보안은 어떻게 신경 썼나요?**
A. API 키는 화면에서 읽을 수 없게 메인 프로세스에서만 쓰고 OS 보안 저장소에 암호화합니다. 엑셀·CSV는 수식 삽입을 막도록 저장하고, xlsx 압축 폭탄과 큰 파일을 제한하고, 저장 형식은 csv·txt만 허용합니다. 다만 상태 저장 파일은 아직 암호화하지 않았습니다.

**Q. 바이브코딩의 약점을 어떻게 보완했나요?**
A. 문제 정의와 요구사항 결정을 제가 먼저 하고(문제 발굴소, 인터뷰), 만든 것은 자동 테스트와 실제 실행으로 확인했습니다. 5번 표처럼 AI가 놓친 것을 실행해 보다가 찾아 테스트로 남겼습니다.

**Q. 개선했다는 걸 어떻게 증명하나요?**
A. 고치기 전에 숫자부터 쟀습니다. 안내 기록 버튼이 보이려면 1280×820에서 1,374px을 내려야 했고, 고친 뒤 0px입니다. 5,000행 목록은 불러오기 0.43초, 조작 0.3~0.4초로 합격선(2초·1초) 안이라 구조는 바꾸지 않았습니다. 숫자와 측정 방법은 `docs/AUDIT.md`, `docs/PERF.md`에 있습니다. 다만 **업무 시간을 얼마나 줄였는지는 측정하지 못했습니다.** 실제 업무에서만 잴 수 있습니다.

**Q. AI가 틀린 적은 없나요?**
A. 있습니다. 한 번은 태그를 올렸다고 보고했는데 명령이 실패해 아무것도 올라가지 않았습니다. 다음 단계 시작 때 확인하다 찾았고, 그 뒤로 단계마다 결과를 다시 확인합니다. 시험이 실패했을 때도 앱 문제인지 시험 문제인지 따로 가려서 고쳤습니다(5-2 표).

**Q. 왜 설치 시험은 안 했나요?**
A. 이 PC에 같은 앱의 이전 버전이 이미 설치돼 있어서, 임시로 설치하면 그 설치 정보를 덮어써 망가뜨릴 수 있었습니다. 그래서 건너뛰고 대신 설치 파일 내용 점검과 **패키지된 앱으로 E2E 전체**를 돌렸습니다. 릴리스 결정이 "조건부 go"인 이유이고, 깨끗한 환경에서 할 절차를 문서(`docs/MANUAL_TESTS.md` M-10)에 남겼습니다.

## 7. 입사 후 하고 싶은 것 (확장 계획)

0. **깨끗한 PC에서 설치·업그레이드·삭제 확인**(릴리스의 남은 조건)과 스크린리더 확인. 그다음 **Supabase 저장소**(범위는 확정: 학습·포트폴리오, 가상 데이터, 안내 기록·메모·주문 메타·설정만. 회사 데이터는 보안 승인 후).
1. **실제 데이터로 검증**: 실제 이메일·공급사 엑셀로 규칙과 머리글 찾기를 다듬고, 놓친 표현을 테스트로 추가.
2. **메일 서버 연결(읽기 전용)**: IT 승인 후 Outlook/Gmail에서 기간·키워드로 메일을 가져오기. 메일 내용을 외부 AI로 보내도 되는지 먼저 확인.
3. **공급사 점수**: 회신율, 납기 변경 횟수, 평균 지연 — 납기 변경 **이력**을 저장해야 의미가 있어 실데이터가 쌓인 뒤에.
4. **효과 측정**: "지연을 알아채는 시간"이 실제로 줄었는지 전후로 재 보기(지금은 측정한 적이 없음).

## 8. 이 프로젝트가 보여 주는 것

- 문제를 먼저 정의하고 요구사항을 정한 뒤 만드는 습관 (문제 발굴소 → 인터뷰 → 기획문서)
- 모르는 것을 지어내지 않고 **(가정)·(미정)**으로 표시하는 태도
- 사람이 확인하는 단계를 설계에 넣는 판단(자동 반영 금지, 근거 문장, 확인 화면)
- 자동 테스트와 실제 실행으로 AI가 만든 결과를 검증하는 방법
- 한계를 숨기지 않는 문서화
- **고치기 전에 재고, 고친 뒤에 다시 재는** 습관 (스크롤 1,374px → 0, 5,000행 0.43초)
- 결정이 필요한 곳에서 멈추고 묻는 것 (확인 필요 주문 처리, 설치 시험을 건너뛴 것, Supabase 범위)
- 요구사항 19개를 자동 시험 결과로 하나씩 점검하고, 못 한 것을 "조건부 go"로 기록한 릴리스 검증(`docs/RELEASE_CHECK.md`)
