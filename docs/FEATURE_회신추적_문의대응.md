# 기획안: 회신 추적 + 연구원 문의 대응 + 첫 화면(홈)

작성: 2026-10-20 · 방식: 사용자 인터뷰 4라운드(질문-답-정리). `grill-with-docs` 문서의 방식을 따랐고, 설치된 스킬을 실행한 것은 아니다 · 상태: **기획만. 구현은 시작하지 않았다.**
반영한 문서: `납기-문제정의/IA.md`, `uj.md`, `prd.md`(v0.3), `docs/erd.md`, `GLOSSARY.md`, `docs/adr/0007·0008`, `docs/screens.json`

> 이 문서의 수치와 기본값은 인터뷰와 가정에서 나왔고 실제 업무 데이터로 검증하지 않았다. 모르는 값에는 (가정)·(미정)을 붙였다.

## 1. 인터뷰로 알게 된 것

| 질문 | 답 | 해석 |
|---|---|---|
| 가장 아쉬웠던 순간 | **연구원이 물어봐서 답할 때** | 앱은 "먼저 알리기"를 돕지만, 연구원이 먼저 물었을 때 **바로 답하는 데** 필요한 정보가 한곳에 없다 |
| 줄여야 할 것 | **놓치는 실수** | 시간이 아니라 누락이 문제다 |
| 디자인 불편 | **어디에 뭐가 있는지 모름** (가장 심한 곳: **처음 열었을 때**) | 첫 화면이 "무엇부터 하라"고 말해 주지 않는다 |
| 연구원이 묻는 것 | 주문 하나의 상태 · 내 주문 전부 · 언제 오는지 · 왜 늦는지 (전부) | 주문 단위와 연구원 단위 두 방향의 요약이 필요하다 |
| 답이 느린 이유 | **정보가 여러 곳에 흩어짐** | 공급사가 한 말(회신)이 앱 밖(메일·전화)에만 있다 |
| 놓치는 실수 모양 | **공급사 회신을 못 봄** | 구체적으로는 **"약속일이 지나도 알려 주는 게 없음"** |
| 답하는 방법 | 이메일, 전화 | 답변 초안은 메일 글과 전화 요점 두 가지 |
| 먼저 만들 것 | **문의 대응(A)과 회신 추적(B)을 합친 것** | 둘은 같은 데이터(회신·약속일)를 쓴다 |

한 문장으로: **"공급사가 약속한 날짜를 기록해 두고, 그 날이 지나면 앱이 먼저 알려 주며, 연구원이 물으면 그 기록으로 한 화면에서 답한다."**

## 2. 기능 한눈에

세 덩어리가 서로 이어진다.

```
 [회신 기록] ──► 약속일이 있다 ──► [회신 늦음 판정] ──► [홈] "회신 늦음 N건"
     │                                                       ▲
     └──► [주문 한눈에 요약] ◄── 연구원이 물어봄 ────────────┘
              └─► [답변 초안] (이메일 글 / 전화 요점)
```

1. **공급사 회신 기록(주문 단위)**: 주문 상세에서 "공급사 회신 받음"을 남긴다. 회신 날짜, **약속일**(도착·회신 예정일), 방법, 메모. 직접 기록이 기본이고, 이메일 폴더에서 읽은 메일은 "회신으로 기록할까요?" 제안만 하고 **사람이 눌러야** 남는다.
2. **회신 늦음 판정**: 가장 최근 회신의 약속일이 기준일보다 지났고, 그 뒤 새 회신이 없고, 입고 완료가 아니면 "회신 늦음"이다. **저장하지 않고 매번 계산한다**(ADR-0008).
3. **문의 대응 요약**: 주문을 누르면 상세 맨 위에 "한눈에"가 생긴다(상태·파일의 납기·공급사 약속일·마지막 공급사 회신·마지막 안내). 연구원으로 필터하면 "이 연구원의 주문 N건" 요약이 위에 붙는다.
4. **답변 초안**: 같은 화면에서 "이메일 답변 복사"와 "전화 요점 복사". 외부로 보내지 않는다.
5. **홈(첫 화면)**: 앱을 켜면 맨 앞 탭에서 "지금 할 일" 세 묶음을 보여 준다.

## 3. 디자인 개선 방향

인터뷰의 불편("어디에 뭐가 있는지 모름, 특히 처음")을 **이미 검증한 패턴**으로 푼다. 클라우드 패널을 고쳤을 때(상태를 크게, 지금 할 일 한 줄, 끝낸 단계는 접기) "알기 쉬워졌다"는 반응을 얻었다.

| 원칙 | 적용 |
|---|---|
| 한 화면은 한 질문에 답한다 | 홈 = "오늘 뭘 해야 하지?", 예외 목록 = "어떤 주문이 문제지?", 오늘 연락할 곳 = "누구에게 연락하지?" |
| 지금 할 일을 맨 위에 크게 | 홈의 세 묶음(안내할 것 · 회신 늦음 · 오늘 연락할 곳). 건수 0이면 "할 일이 없어요"로 끝낸다 |
| 처음이면 순서를 알려 준다 | 파일이 없거나 기록이 없을 때 "① 목록 열기 → ② 예외 목록 → ③ 안내 기록" 3단계 안내(HM-24-A). 끝낸 단계는 접는다 |
| 탭 이름이 일의 순서를 따른다 | 홈 → 예외 목록 → 오늘 연락할 곳 → 지연 분석 → 보고서 (탭 5개, IA의 "4~5개 유지" 안) |
| 상세 맨 위에 요약 | 긴 상세(안내·메모·안내문·원인·대체품…)를 읽기 전에 "한눈에"로 답이 나온다 |
| 색·글자는 지금 체계를 따른다 | 지연=장미, 임박=호박, 정상=민트, 회신 늦음은 **호박+"N일째"** 글자(색에만 기대지 않는다) |

## 4. 결정 표 (되돌리기 어려운 것은 ADR로)

| 결정 | 내용 | 근거 | 기록 |
|---|---|---|---|
| 약속일은 **주문 단위** | "PO-1002는 10/30 도착"처럼 주문번호에 붙인다 | 연구원은 주문 단위로 묻는다. 공급사 단위로는 "이 주문은 언제?"에 못 답한다 | ADR-0007 |
| 새 표 `order_replies` | 기존 `supplier_contact_logs`(공급사 단위 연락)에 열을 얹지 않는다 | 공급사 단위와 주문 단위 약속이 섞이면 "오늘 연락할 곳" 계산이 틀어진다 | ADR-0007 |
| 로컬 저장 형식 **v3** | `orderReplies` 목록을 더한다. v2→v3은 빈 목록 추가라 되돌리기 쉽다 | 기록마다 id·시각·삭제 표시(v2 규칙 그대로) | ADR-0007 |
| 회신 늦음은 **계산** | 상태를 저장하지 않는다. 기준일이 바뀌면 바로 달라진다 | 저장하면 기준일·기록과 어긋난다 | ADR-0008 |
| 알림은 **앱 안에서만** | 홈과 목록에 보여 준다. Windows 알림은 만들지 않는다 | 하루 한 번 여는 업무 방식에 맞고, 구현이 단순하다 | ADR-0008 |
| 이메일 연동은 **제안만** | 메일에서 회신 같은 것을 찾아 "기록할까요?"로 묻는다. 자동 기록은 하지 않는다 | 틀린 약속일이 쌓이면 "회신 늦음"이 거짓으로 울린다 | PRD FR-25 |
| 클라우드에도 올린다 | 새 기록은 기존 올리기·복원 규칙(append-only, 장부 비교)을 그대로 따른다 | 로컬이 기준, DB는 사본(ADR-0002, 0006) | erd.md |

## 5. 범위

**한다(이 기획안)**: 회신 기록, 회신 늦음 판정, 문의 대응 요약(주문·연구원), 답변 초안(이메일·전화), 이메일 폴더에서 회신 기록 제안, 홈 탭, 처음 시작 안내.
**하지 않는다**: Windows 알림, 공급사에게 메일 자동 발송, 여러 사람이 같이 쓰기, 회신 내용 자동 요약(AI), 실제 메일 서버 연결.
**기존 범위 밖이던 것을 일부 끌어온다**: 이메일 납기 추출(S2)과 오늘 연락할 곳(S3)은 PRD가 "범위 밖"으로 뒀지만, 이 기능이 두 화면의 결과를 읽는다. 두 화면의 **동작은 바꾸지 않고** 읽기만 한다.

## 6. 데이터 변경 요약

- **새 표 `order_replies`** (쌓는 기록: 넣기와 삭제 표시만): `id, user_id, order_no, replied_on, promised_on, channel, note, source, created_at, deleted_at, deleted_reason`. 상세는 `docs/erd.md`.
- 로컬 v3: `orderReplies: { 주문번호: [기록…] }`, 주문당 살아 있는 기록 20건 상한(가정).
- 올리기·복원: `rows.js`에 표 하나가 늘고, 복원은 "로컬에 없는 id만" 규칙 그대로. DB 규칙(RLS·열 단위 권한)은 기존 표와 같은 패턴으로 만든다.
- 설정 저장(`user_settings`)과 다른 표는 바뀌지 않는다.

## 7. 열린 질문 (구현 전에 정할 것)

| # | 질문 | 임시 기본값 |
|---|---|---|
| 1 | 약속일이 지난 뒤 "아직 안 왔어요"로 넘기는 방법이 필요한가? (홈에서 같은 건이 계속 울린다) | 새 회신을 남기거나 공급사 "연락함" 기록을 하면 그날은 조용해진다 (미정) |
| 2 | 한 주문에 약속일이 여러 번 바뀌면? | 가장 최근 회신의 약속일이 이긴다. 이전 기록은 이력으로 남는다 |
| 3 | 연구원 요약은 어떤 건을 담나? | 그 연구원의 지연·임박·확인 필요 주문 전부 (입고 완료 제외) |
| 4 | 이메일에서 회신을 알아보는 규칙은? | 이메일 납기 추출의 기존 결과(날짜+근거 문장)를 쓰고, 신뢰도가 낮으면 제안하지 않는다 |
| 5 | 홈의 "안내할 것"과 예외 목록의 안내 막대가 겹치지 않나? | 홈은 건수와 상위 3건만 보여 주고 "예외 목록에서 보기"로 넘긴다 |
| 6 | 회신 기록 한 건의 글자 수 | 메모 200자(다른 기록과 같은 규칙, 가정) |

## 8. 구현 순서 제안 (아직 시작하지 않음)

1. 로컬 v3 + `orderReplies` + 판정 함수(`src/replies.js`, 순수 함수)와 단위 시험. (DB와 무관하게 되돌릴 수 있다)
2. 주문 상세: 회신 기록(LS-37-A)과 한눈에 요약(LS-38-A), 답변 초안(LS-39-A).
3. 홈 탭(HM-11-T)과 처음 시작 안내(HM-24-A).
4. 연구원 문의 요약(LS-27-A).
5. DB: `order_replies` 마이그레이션, 올리기·복원, 계약·E2E 시험.
6. 이메일 폴더에서 회신 기록 제안(FR-25).

각 단계는 시험이 통과한 뒤 다음으로 간다. 실제 쓰임(문의 응답 시간, 회신 늦음 감지)은 입사 후 기준선을 재서 확인한다(PRD 7절).
