# ADR-0007: 공급사 회신·약속일은 주문 단위 새 표(`order_replies`)로 두고, 로컬 저장 형식을 v3로 올린다

- 날짜: 2026-10-20
- 상태: **계획 결정** (기획 단계. 구현·DB 적용 전). 근거: `docs/FEATURE_회신추적_문의대응.md` 인터뷰

## 결정
- 공급사가 알려 준 회신과 약속일(도착·회신 예정일)을 **주문번호에 붙여** 기록한다. 새 쌓는 기록 표 `order_replies`를 만든다(넣기와 삭제 표시만, 고치거나 지우지 않는다).
- 기존 `supplier_contact_logs`(공급사 단위 연락 기록)는 바꾸지 않는다.
- 로컬 저장 형식은 v3로 올려 `orderReplies` 목록을 더한다. v2 → v3 이전은 빈 목록을 추가하는 것뿐이다.

## 왜 되돌리기 어려운가 / 왜 의외인가
- 새 표는 DB에 한 번 만들면 이름·열을 바꾸기 번거롭고, 이미 올라간 행이 생긴다.
- "공급사 연락 기록에 `order_no` 열 하나만 얹으면 되지 않나?"가 더 작은 변경처럼 보인다. 그러나 그 표는 공급사 단위로 **"오늘 연락할 곳"** 을 계산하는 데 쓰인다. 같은 표에 주문 단위 약속일이 섞이면, 한 공급사의 여러 주문 약속일이 공급사 단위 계산을 흔든다.

## 대안과 버린 이유
- **`supplier_contact_logs`에 `order_no`(null 허용) 추가**: 표는 안 늘지만 두 종류의 의미가 한 표에 섞인다. 버렸다.
- **공급사 단위 약속일**: 구조는 가장 간단하지만 연구원의 질문("이 주문은 언제 와요?")에 답하지 못한다. 인터뷰에서 주문 단위로 정했다.
- **주문 메타(`order_meta`)에 약속일 한 칸**: 이력이 안 남고 "회신 받음"이라는 사건을 기록하지 못한다. 최신 값만 남는 구조라 버렸다.

## 결과
- DB: 기존 쌓는 기록 표와 같은 패턴(`id uuid`, `user_id default auth.uid()`, RLS, 열 단위 권한, `deleted_at`·`deleted_reason` 일관성 제약, 글자 수 제약)으로 만든다. 상세는 `docs/erd.md`.
- 로컬: `orderReplies: { 주문번호: [{ id, date, promised, channel, note, source, createdAt, deletedAt?, deletedReason? }] }`, 주문당 살아 있는 기록 20건 상한(가정). 한도에 밀리면 이유 `cap`.
- 올리기·복원: `src/sync/rows.js`에 표가 하나 늘 뿐 규칙(장부 비교, 로컬에 없는 id만 복원)은 같다(ADR-0006).
- 주문번호가 겹칠 수 있다는 미검증 가정(ADR-0004)이 이 표에도 그대로 걸린다.
