## 합격선(KR)

- **목표값은 정하지 않았다.** 입사 후 기준선을 먼저 재고 정한다 (PRD 7절).
- 지금 정할 수 있는 것은 **측정 방법**뿐이다: 선제 안내 비율, 지연 미안내 건 수, 안내 기록률, 안내 건당 소요 시간, 재안내 누락 건 수, 수동 매핑 비율, 메모 건 수.
- 자동 테스트의 합격선: **기존 테스트를 약하게 바꾸지 않고, 모든 테스트가 통과**해야 한다.

## Phase 2에서 정한 것 (devpian.md와 달라지거나 더해진 것)

| ID | 결정 | 이유 |
|---|---|---|
| P2-1 | 안내 기록 **취소는 화면 코드(`informed.js`)를 바꾸지 않고**, 저장소가 이전 상태와 비교해 `deletedAt`을 남긴다 (`core.fromView`). `devpian.md` T2.3(`append`/`undo`를 바꾸기)을 대체 | 같은 결과(삭제 흔적, 규칙이 삭제된 기록을 무시)를 변경 없이 얻고, 기존 테스트가 그대로 지켜진다. 삭제는 저장의 문제이지 화면 규칙의 문제가 아니다 |
| P2-2 | 화면과 메인 프로세스 사이의 IPC `state-load/save/clear`는 **이름과 모양을 그대로** 두고, 알림을 전달하는 `state-info`만 더했다 | 화면 변경 최소화 (D-3). 이전·손상·읽기 전용을 사용자에게 알려야 해서 필요 |
| P2-3 | 저장소 인터페이스는 **비동기** (`load/save/clear`가 Promise) | 나중의 DB 저장소가 비동기이므로 지금부터 맞춘다. 같은 저장소의 동작은 차례로 처리 |
| P2-4 | **읽을 수 없다고 빈 상태로 덮어쓰지 않는다.** 깨진 파일은 `state.corrupt-<시각>.json`으로 옮겨 보관한 뒤 빈 상태로 시작. 더 새로운 버전·열기 실패·백업 실패·이전 실패는 **읽기 전용**(보이되 저장만 막음) | 사용자 데이터를 잃는 것이 가장 큰 위험 (R-1). `devpian.md` D-4.4 |
| P2-5 | 백업은 `state.v0.bak.json`. 이미 있고 **내용이 같으면** 그대로 쓰고, **다르면** `state.v0.bak-<시각>.json`으로 새로 만든다 (덮어쓰지 않는다) | 처음 계획은 "있으면 덮어쓰지 않는다"였는데, 그러면 다른 내용의 새 원본이 백업되지 않는 구멍이 있다 |
| P2-6 | 읽기만 해서는 파일을 만들지 않는다 | 앱을 열어 보기만 했는데 디스크가 바뀌면 안 된다 |
| P2-7 | 계약 테스트는 `test/store.contract.test.js` 한 파일에서 저장소 구현마다 반복 실행한다 (`devpian.md`의 `test/store.contract.js`와 이름이 다름) | `node --test`가 `test/`의 모든 .js를 테스트로 실행하므로, 시험이 없는 도우미 파일을 두면 가짜 테스트로 집계된다 |
| P2-8 | 이전된 예전 안내 기록의 `createdAt`은 **기록한 날짜의 정오(UTC)**. 실제 시각을 모르기 때문 | 가짜 정밀도를 만들지 않고 날짜 순서는 지킨다 |
| P2-9 | 주문당 삭제 표시는 최근 100건까지만 보관 | 파일이 끝없이 커지지 않게. 삭제 전달이 필요한 범위는 최근 기록이다 |
