# spec-plan 참고: 검증 목록과 조사한 출처

## spec 검증 목록 (plan으로 넘어가기 전)

- [ ] 6칸이 모두 채워져 있다 (빈 칸은 이유가 적혀 있다)
- [ ] 문제가 "누가 / 무엇을 못 해서 / 어떤 일이 생기나"의 한 문장으로 말해진다
- [ ] 사용자 장면마다 우선순위(P1, P2)가 있고, P1만 만들어도 쓸모가 있다
- [ ] 모든 요구사항에 번호와 우선순위, **시험할 수 있는** 수용 기준이 있다
- [ ] 엣지 케이스(빈 값, 한도, 중복, 실패)가 실제 사례로 적혀 있다
- [ ] 성공 기준이 숫자나 화면에 보이는 것으로 적혀 있고, 기술 이름이 없다
- [ ] 제외 범위에 이유가 있다 (없으면 범위가 슬며시 커진다)
- [ ] 확인 필요가 **3개 이하**이고, 각각 임시 기본값이 있다
- [ ] 용어가 IA 5절·GLOSSARY와 같고 금지어가 없다
- [ ] PRD의 FR 번호·IA의 화면 ID·UJ의 CUJ와 모순이 없다

## plan 검증 목록 (개발로 넘어가기 전)

- [ ] 모든 FR·SC가 시험 표에서 한 군데 이상 확인된다
- [ ] 단계마다 끝 조건과 되돌리는 법이 있다
- [ ] 새 라이브러리가 없거나, 있으면 이유·정확한 버전·대안이 있다
- [ ] 버전이 파일에서 읽은 값이다 (추측 아님)
- [ ] 바뀌는 데이터 구조는 ERD·DATA_MODEL·ADR 갱신이 단계에 들어 있다
- [ ] 항상/먼저 묻는다/절대 안 한다 경계가 적혀 있다
- [ ] 지금 돌아가는 기능을 지키는 시험이 있다
- [ ] `CLAUDE.md` 규칙 점검을 했다

## 조사한 출처 (2026-10-20, 웹)

사람이 쓴 요약이 섞여 있어서 아래는 "이 스킬에 반영한 아이디어"이고, 각 도구의 공식 문서와 다를 수 있다.

| 출처 | 가져온 것 |
|---|---|
| [GitHub Spec Kit — spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md) | 우선순위(P1~)가 붙은 사용자 이야기, 각 이야기의 "혼자 시험할 수 있는 조각"과 Given/When/Then, 엣지 케이스, 번호 붙은 기능 요구사항(FR-###), 측정 가능하고 기술 중립인 성공 기준(SC-###), 가정, 모호한 것은 `NEEDS CLARIFICATION` 표시 |
| [GitHub Spec Kit — plan-template.md](https://github.com/github/spec-kit/blob/main/templates/plan-template.md) | 기술 맥락(언어·버전, 주요 의존성, 저장소, 테스트, 대상 환경, 성능 목표, 제약, 규모), 프로젝트 규칙(헌법) 점검, 실제 폴더 구조 하나만 남기기, 규칙을 어길 때만 "복잡도 추적" |
| [Spec Kit 설명 모음(skills.sh)](https://skills.sh/ahgraber/skills/spec-kit-specify) | 확인 필요는 **최대 3개**, 영향 순서(범위 → 보안·개인정보 → 사용성 → 기술 세부), 나머지는 합리적 기본값, "계획 준비 완료"는 미해결 표시가 0개 |
| [Kiro 스펙 설명(codemyspec)](https://codemyspec.com/blog/kiro-specs-explained) | 요구사항 → 설계 → 작업의 단계별 승인, 수용 기준을 EARS 문형(WHEN 조건 THE SYSTEM SHALL 결과)으로 쓰기, 작업을 요구사항에 연결 |
| [How to write a good spec for AI agents — Addy Osmani](https://addyosmani.com/blog/good-spec/) | 스펙에 들어갈 여섯 영역(명령, 시험, 프로젝트 구조, 코드 스타일, 깃 작업 방식, 경계), 경계의 3단계(항상 / 먼저 묻는다 / 절대 안 한다), 너무 큰 스펙은 실패하니 작게, 읽기 전용으로 먼저 계획, 스펙은 살아 있는 문서 |

## 우리 프로젝트에 맞게 바꾼 점

- 사용자가 정한 칸(spec 6칸, plan 5칸)을 **그대로 유지**하고, 조사한 요소는 칸 안으로 넣었다(별도 칸을 늘리지 않음).
- "확인 필요"의 3개 제한과 "plan 전에 0개" 규칙은 Spec Kit에서 가져왔다.
- 경계 3단계는 plan의 "제약과 주의점" 칸에 넣었다.
- 요구사항 번호는 새로 만들지 않고 **PRD의 FR 번호**를 쓴다(문서가 갈라지지 않게).
- 수용 기준은 EARS를 우리 말로 옮겼다: "~할 때 ~해야 한다".
