# spec-plan: 의도 → spec.md → plan.md

이 프로젝트(납기 알리미)의 작업 순서는 **Intent → spec → plan → 개발 → 문서 갱신**이다(`CLAUDE.md`). 이 스킬은 가운데 두 문서를 만든다.

- **spec.md** = **무엇을, 왜** 만드나 (여섯 칸). 기술 이야기를 하지 않는다.
- **plan.md** = **어떻게** 만드나 (다섯 칸). spec의 번호(FR-xx, SC-xx)를 그대로 가리킨다.

두 파일은 저장소 루트에 둔다(`Intent.md`와 같은 자리). 작업이 끝나면 셋을 `docs/specs/날짜-이름/`으로 옮겨 보관하고 다음 작업을 새로 쓴다.

## 하지 않는 것
- 코드를 짜지 않는다. 이 스킬의 결과물은 문서 두 개뿐이다.
- 문서에 없는 결정을 임의로 정해 넣지 않는다. 모르면 spec의 "확인 필요"에 적고 사용자에게 묻는다.
- 사용자가 승인하기 전에 plan을 확정하지 않는다(spec 승인 → plan 작성 → plan 승인).

## 순서

### 1. 읽기 (읽은 파일을 마지막 보고에 적는다)
1. `Intent.md` — 문제·기대 결과·영향 범위·제약·열린 질문. 비어 있거나 요청과 다르면 **먼저 Intent를 고친다.**
2. `../납기-문제정의/prd.md` 해당 FR의 수용 기준·지표·가정, `uj.md` CUJ, `IA.md` 화면 ID와 용어(5절).
3. `docs/erd.md`, `docs/DATA_MODEL.md`, `docs/adr/` — 데이터와 되돌리기 어려운 결정.
4. `GLOSSARY.md`, `CLAUDE.md`(규칙), `package.json`(정확한 버전), 비슷한 기존 기능의 코드.

### 2. spec.md 쓰기 — `templates/spec.md`를 채운다
- 여섯 칸을 모두 채운다: 문제 / 주요 사용자 / 핵심 기능과 요구사항 / 성공 기준 / 제외 범위 / 확인 필요.
- 요구사항 번호는 **PRD의 FR 번호를 재사용**한다(새로 만들면 PRD에도 넣는다). 성공 기준은 SC-01부터.
- 모르는 것은 임시 기본값을 적고 "확인 필요"에 올린다. **확인 필요는 최대 3개**, 영향이 큰 순서(범위 → 보안·개인정보 → 사용성 → 기술 세부)로 남기고 나머지는 합리적인 기본값으로 정한다(가정으로 표시).
- 확인 필요가 있으면 `AskUserQuestion`으로 한 번에 모아 묻는다(추천 기본값을 첫 번째 선택지로). 답을 받으면 칸에서 지우고 결정 표로 옮긴다.
- **spec 검증 목록**(`reference.md`)을 통과해야 plan으로 넘어간다. 통과하지 못한 항목을 사용자에게 보여 주고 승인을 받는다.

### 3. plan.md 쓰기 — `templates/plan.md`를 채운다
- 다섯 칸: 기술과 버전 / 구조와 파일 / 단계별 접근 / 테스트 전략 / 제약과 주의점.
- 모든 FR이 **어느 단계에서, 어느 파일에서, 어느 시험으로** 확인되는지 표로 보인다(빠진 FR이 없어야 한다).
- 새 라이브러리는 되도록 들이지 않는다. 들이면 이유와 정확한 버전, 대안, 되돌리는 법을 적는다.
- 프로젝트 규칙 점검(`CLAUDE.md`)을 한 번 하고, 어긋나면 이유를 적는다.
- 데이터 구조가 바뀌면 ERD·DATA_MODEL·ADR을 같이 고칠 것을 단계에 넣는다.

### 4. 마무리
- `Intent.md`의 "연결 문서"에 spec.md·plan.md를 추가한다.
- 결과를 한 번에 보고한다: 만든 파일, 읽은 문서, 남은 확인 필요, 다음 행동(승인 요청).
- 사용자가 승인하면 그때 개발을 시작한다(`CLAUDE.md`의 작업 순서 4단계).

## 쓰는 법의 원칙 (쉬운 말)
- 한 문장은 한 가지만 말한다. "~해야 한다"로 끝나는 요구사항은 시험할 수 있어야 한다.
- 성공 기준은 **눈으로 확인**할 수 있게 쓴다(어느 화면에서 무엇이 어떻게 보이는지, 숫자로).
- 용어는 `IA.md` 5절과 `GLOSSARY.md`를 따른다(금지어: 재안내, 확인필요, 안내완료, 입고완료).
- 길게 쓰지 않는다. 큰 문서는 읽는 사람도 AI도 놓친다. 한 칸이 한 화면을 넘으면 줄인다.
- 문서는 살아 있다. 구현 중에 알게 된 것은 바로 고치고, 고친 날짜를 남긴다.

참고 출처와 검증 목록은 `reference.md`.
